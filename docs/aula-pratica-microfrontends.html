Como usar esta aula

Siga na ordem. Cada bloco de código tem antes um parágrafo dizendo para que ele serve, o caminho do arquivo no cabeçalho e um botão Copiar. Os comentários dentro do código explicam linha a linha. Todos os comandos são executados na raiz do projeto, no PowerShell ou no terminal do VS Code.

Dica: no VS Code, ao criar um arquivo digitando o caminho completo (ex.: apps/cardapio/data/pratos.js), as pastas são criadas automaticamente.

1Visão geral da tecnologia

O que são Micro Frontends

É dividir um frontend grande em aplicações menores e independentes, cada uma podendo ser desenvolvida, testada e publicada por um time diferente. Uma aplicação principal, o container (ou host), junta as partes numa tela só.

Por que usar Module Federation

O Module Federation (recurso do Webpack 5) permite que uma aplicação importe componentes de outra aplicação em tempo de execução, pela rede, como se fossem locais. Isso garante o principal benefício dos micro frontends: publicar um micro não exige recompilar o container. Também permite compartilhar bibliotecas (como o React) para que o usuário não baixe a mesma coisa três vezes.

Comunicação entre os micros

Quando o usuário clica em "Adicionar ao pedido", o Cardápio dispara um CustomEvent chamado pedido:item-adicionado no window, levando { id, nome, preco }. O Pedido escuta esse evento e atualiza a lista. Como nenhum micro conhece o outro, cada um continua independente.

Por que Next 14 com Pages Router

O plugin @module-federation/nextjs-mf só suporta Next.js 12 a 15 com Pages Router (pasta pages/). App Router e Next 16 não funcionam. As versões desta aula são fixas e foram testadas juntas: não troque por versões mais novas.

2Estrutura final

Este é o mapa do que você vai construir. São três projetos Next.js independentes dentro de apps/, cada um com sua própria porta e configuração, organizados por responsabilidade: components/ para a interface, events/ para a comunicação, hooks/ para lógica e data/ para dados. Volte aqui sempre que não souber onde um arquivo deve ficar.

3Raiz do monorepo

Antes de tudo, confirme que o Node.js e o npm estão instalados. O Next 14 exige Node 18.17 ou superior. Se algum comando não for reconhecido, instale a versão LTS do Node em nodejs.org (o npm vem junto) e reabra o terminal.

O package.json da raiz transforma a pasta num monorepo: com workspaces, o npm trata cada pasta de apps/ como um projeto, mas instala tudo de uma vez numa única node_modules. Os scripts sobem os três apps com um comando só. O bloco overrides é essencial: trava o webpack e o enhanced-resolve em versões compatíveis, porque as mais novas quebram o plugin. JSON não aceita comentários, por isso a explicação fica aqui.

O .gitignore lista o que o git deve ignorar. node_modules tem centenas de MB e é recriada com npm install; .next é gerada a cada build. Nenhuma das duas deve ir para o GitHub: deixariam o repositório pesado e cheio de arquivos que não são seu código.

4package.json dos três apps

Cada app tem seu próprio package.json. Os três são iguais, mudam só o name (usado no -w) e a porta (-p). Os scripts usam cross-env NEXT_PRIVATE_LOCAL_WEBPACK=true: essa variável obriga o Next a usar o webpack instalado no projeto em vez da cópia interna dele, condição para o plugin de federação funcionar. O cross-env faz a variável funcionar igual no Windows, Mac e Linux. As versões não têm ^, então o npm instala exatamente as que foram testadas.

ScriptO que faz
devServidor de desenvolvimento, recarrega ao salvar
buildCompila a versão otimizada de produção
startSobe a versão compilada pelo build

Com os quatro package.json prontos, instale tudo a partir da raiz. O npm lê os workspaces, aplica os overrides e cria uma única node_modules e o package-lock.json, que registra as versões exatas instaladas. Pode aparecer um aviso de que o nextjs-mf será descontinuado: é esperado e pode ser ignorado.

5Micro Cardápio

Os dados do cardápio ficam separados dos componentes, em data/. Assim, trocar ou ampliar o cardápio não exige mexer em JSX. O id é a peça mais importante: identifica cada prato de forma única, serve de key no React e é o que o Pedido usa para saber se o prato já está na lista.

Este arquivo é o contrato entre os micros: define o nome do evento e a função que o dispara. Ele será copiado, idêntico, para o Pedido. Centralizar o nome numa constante evita erros de digitação, que falham em silêncio: o navegador não avisa quando ninguém escuta um evento. O CustomEvent leva os dados em detail, e o window funciona como um "alto-falante" que toda a página ouve.

Laranja = Cardápio · Verde = navegador · Azul = Pedido. Nenhuma etapa importa código do outro micro.

O PratoCard mostra um único prato. Ele é propositalmente "burro": não sabe que existe evento nem pedido, só chama onAdicionar quando o botão é clicado. Separar o visual da lógica deixa o componente reutilizável e simples de testar. O Intl.NumberFormat nativo formata 39.9 como R$ 39,90 sem biblioteca extra.

O Cardapio é o componente principal do micro e o único que será exposto ao container. Ele percorre a lista de pratos e liga cada card ao evento do contrato. Repare que o evento envia só id, nome e preco: a descrição é assunto do Cardápio, não do Pedido. Contratos enxutos são mais fáceis de manter.

Os estilos usam CSS Modules (.module.css): o Next renomeia cada classe com um sufixo único, então o .card do Cardápio nunca colide com estilos do container ou do Pedido. Isso é essencial em micro frontends, onde vários times estilizam a mesma página. O grid com auto-fill e minmax é responsivo sem precisar de media query.

O CSS global define o básico da página: box-sizing, fonte e cores. Ele só afeta o app que o importa, então quando o Cardápio roda dentro do container, quem manda nos estilos globais é o container. Por isso os três apps têm um globals.css igual: a aparência fica consistente rodando sozinho ou integrado.

No Pages Router, _app.js é o "molde" que envolve todas as páginas do app. É o único lugar onde o Next permite importar CSS global, por isso o globals.css entra aqui. Component é a página atual e pageProps são os dados dela.

Esta página existe só para rodar e testar o Cardápio sozinho, na porta 3001, como um time faria antes de integrar. Ela não é exposta: o container recebe apenas o componente Cardapio. O useEffect escuta o próprio evento e o mostra no console, provando que o clique está disparando os dados certos.

Testar o Cardápio isolado

Suba só o Cardápio e confira no console do navegador se o evento sai corretamente. Testar cada micro isoladamente é exigência da tarefa e separa problemas do próprio micro de problemas de integração, que só aparecem no container.

Abra localhost:3001, pressione F12 → Console e clique em "Adicionar ao pedido". Deve aparecer [cardapio] evento emitido: {id: 'lasanha', ...}.

6Micro Pedido

Primeiro, o mesmo contrato do Cardápio, copiado sem nenhuma alteração. Parece duplicação, mas é proposital: se o Pedido importasse esse arquivo do Cardápio, os dois deixariam de ser independentes. Em projetos maiores, o contrato costuma virar um pacote npm compartilhado.

O hook usePedido concentra toda a lógica do Pedido: guarda os itens, escuta o evento e oferece remover, limpar e o total. O ponto mais delicado é o cleanup do useEffect. Em desenvolvimento, o reactStrictMode monta, desmonta e monta de novo cada componente. Sem remover o listener, sobram dois ouvintes e cada clique adiciona o prato em dobro.

Por que o cleanup é obrigatório (StrictMode em dev)

❌ Sem cleanup

  1. monta → registra ouvinte 1
  2. desmonta → ouvinte 1 continua
  3. monta → registra ouvinte 2
1 clique = 2 lasanhas

✅ Com cleanup

  1. monta → registra ouvinte 1
  2. desmonta → remove ouvinte 1
  3. monta → registra ouvinte 2
1 clique = 1 lasanha

Mesmo id soma a quantidade; id novo cria uma linha. Total: 2 × 39,90 + 44,50 = R$ 124,30.

O componente Pedido só exibe o que o hook entrega: lista, subtotal de cada linha, total e botões. Também é o componente exposto ao container. Ele trata o estado vazio com uma mensagem útil e usa atributos de acessibilidade (aria-label no ✕ e aria-live no total) para que leitores de tela entendam a interface.

Estilos do Pedido, também em CSS Module. Cada linha usa um grid de três colunas: o nome ocupa o espaço que sobra (1fr), enquanto subtotal e botão ficam com o tamanho do próprio conteúdo (auto). Assim os valores ficam alinhados à direita em qualquer largura de tela.

CSS global e _app.js iguais aos do Cardápio. Mesmo que repitam conteúdo, cada app precisa dos seus, porque cada um é um projeto Next independente e precisa funcionar sozinho na sua porta, com a mesma aparência que terá dentro do container.

Página de teste isolado do Pedido. Como o Cardápio não existe na porta 3002, o botão "Simular item adicionado" faz o papel dele, disparando o mesmo evento do contrato. É uma forma barata de testar um micro que depende de outro, sem precisar subir os dois.

Testar o Pedido isolado

Suba só o Pedido e use o simulador. Clicando duas vezes, deve aparecer uma linha com 2× Prato de teste · R$ 20,00. Se aparecerem duas linhas, revise a busca por id; se aparecer 4×, revise o cleanup do usePedido.

7Module Federation nos micros

O next.config.js transforma o Cardápio num remote. O NextFederationPlugin é acrescentado ao webpack do Next e publica um remoteEntry.js com a lista do que pode ser importado de fora. name é a identidade do remote e exposes liga um nome público (./Cardapio) ao arquivo real. React e React DOM já são compartilhados pelo próprio plugin, por isso shared fica vazio.

Como um import do container chega ao arquivo do Cardápio
import('cardapio/Cardapio')no container
→
remotes.cardapioURL do remoteEntry :3001
→
remoteEntry.jsíndice publicado pelo Cardápio
→
exposes['./Cardapio']components/Cardapio.jsx

Por isso name, a chave em remotes e a chave em exposes precisam bater exatamente.

A mesma configuração para o Pedido, mudando apenas o name e o que é exposto. O container vai importar pedido/Pedido, que aponta para components/Pedido.jsx. O hook usePedido não precisa ser exposto: ele vai junto, por ser importado pelo componente.

Verificar se os remotes estão publicando

Antes de criar o container, confirme que cada remote publica o seu remoteEntry.js. Em modo dev, o Next só compila quando a página é visitada pela primeira vez. Por isso, abra a página do micro antes de abrir o arquivo.

Abra localhost:3001 e depois localhost:3001/_next/static/chunks/remoteEntry.js. Se aparecer código JavaScript, o remote está funcionando.

8Container App

No container, em vez de exposes usamos remotes: o endereço de cada micro no formato nome@url. A chave (cardapio) vira o prefixo dos imports. A função recebe isServer porque o Next compila o app duas vezes, uma para o servidor e outra para o navegador, e cada compilação precisa do seu remoteEntry.js.

Duas compilações, dois remoteEntry

Servidor (isServer = true)

/_next/static/ssr/remoteEntry.js

Usado quando o Next gera o HTML no servidor.

Navegador (isServer = false)

/_next/static/chunks/remoteEntry.js

Usado quando o código roda no navegador do usuário.

O Error Boundary é uma rede de proteção em volta de cada micro. Se um micro lançar um erro ao renderizar, só a área dele mostra um aviso, e o resto da página continua funcionando. É o isolamento de falhas que justifica micro frontends. Precisa ser um componente de classe porque o React não tem hook para capturar erros de renderização.

O CSS global do container. Quando os micros rodam dentro dele, estes são os estilos globais que valem na página, inclusive para os componentes do Cardápio e do Pedido. Os estilos específicos de cada micro continuam vindo dos CSS Modules deles, baixados junto com o código remoto.

O layout da página principal segue a abordagem mobile-first: o estilo padrão é para celular (uma coluna) e a media query acrescenta as duas colunas a partir de 900px. No desktop, o pedido fica sticky: permanece visível enquanto você rola o cardápio, então o usuário vê o total mudar a cada clique.

O _app.js do container, igual ao dos micros: envolve as páginas e importa o CSS global. Ele é o "dono" da página quando tudo roda junto, então é o globals.css importado aqui que vale em localhost:3000, mesmo para os componentes vindos dos micros.

A página principal junta tudo. React.lazy com import('cardapio/Cardapio') baixa o código do micro pela rede só quando ele for renderizado, e o Suspense mostra "Carregando…" enquanto isso. O estado noNavegador garante que os micros só sejam montados no navegador, evitando erros de hidratação do Pages Router com componentes remotos. Cada micro fica dentro de um MicroBoundary.

Um erro 404 por página é o navegador procurando o favicon.ico (os apps não têm ícone): é inofensivo. Se o container ficar em "Carregando…" na primeira vez, abra localhost:3001 e localhost:3002 uma vez (o modo dev compila sob demanda) e recarregue o 3000.

10Build de produção

O modo dev esconde alguns problemas que só aparecem na versão compilada. O build gera a versão otimizada dos três apps e precisa terminar sem erros; o start sobe essa versão nas mesmas portas. Repita o teste de integração em localhost:3000 para garantir que a entrega funciona de verdade.
