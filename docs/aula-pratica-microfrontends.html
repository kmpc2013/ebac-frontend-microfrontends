Como usar esta aula

Siga na ordem. Cada bloco de código mostra o caminho do arquivo no cabeçalho e tem um botão Copiar. Todos os comandos são executados na raiz do projeto (a pasta ebac-frontend-microfrontends), no PowerShell ou no terminal do VS Code.

1Visão geral da tecnologia

O que são Micro Frontends

É dividir um frontend grande em aplicações menores e independentes, cada uma podendo ser desenvolvida, testada e publicada por um time diferente. Uma aplicação principal, o container (ou host), junta as partes numa tela só.

Por que usar Module Federation

O Module Federation (recurso do Webpack 5) permite que uma aplicação importe componentes de outra aplicação em tempo de execução, pela rede, como se fossem locais. Isso garante o principal benefício dos micro frontends: publicar um micro não exige recompilar o container. Também permite compartilhar bibliotecas (como o React) para que o usuário não baixe a mesma coisa três vezes.

Comunicação entre os micros

Quando o usuário clica em "Adicionar ao pedido", o Cardápio dispara um CustomEvent chamado pedido:item-adicionado no window, levando { id, nome, preco }. O Pedido escuta esse evento e atualiza a lista. Como nenhum micro conhece o outro, cada um continua independente.

Por que Next 14 com Pages Router

O plugin @module-federation/nextjs-mf só suporta Next.js 12 a 15 com Pages Router (pasta pages/). App Router e Next 16 não funcionam. As versões desta aula são fixas e foram testadas juntas: não troque por versões mais novas.

3Raiz do monorepo

Confira se o Node.js está instalado (versão 18.17 ou superior):

  • workspaces: transforma a raiz num monorepo. Cada pasta em apps/ é um projeto, mas o npm install roda uma vez só, na raiz.
  • scripts: npm run dev sobe os três apps juntos com o concurrently; -w cardapio roda o script dentro daquele app.
  • overrides: trava o webpack e o enhanced-resolve em versões compatíveis. Versões mais novas quebram o plugin (veja Problemas comuns).

Impede que dependências e arquivos gerados pelo build subam para o GitHub.

4package.json dos três apps

Os três são iguais, mudam apenas o name e a porta.

  • NEXT_PRIVATE_LOCAL_WEBPACK=true: obriga o Next a usar o webpack instalado no projeto, em vez da cópia interna dele. O plugin de federação precisa disso.
  • cross-env: permite definir a variável de ambiente do mesmo jeito no Windows, Mac e Linux.
  • -p 3001: porta de cada app.
  • Versões sem ^: instalam exatamente a versão testada.

5Micro Cardápio

Os dados do cardápio. O id identifica cada prato de forma única (usado como key e para agrupar no pedido).

O contrato: nome do evento e função que o dispara. CustomEvent carrega os dados em detail; window.dispatchEvent "anuncia" para quem estiver escutando. O typeof window evita erro quando o Next renderiza no servidor, onde não existe window.

Componente visual de um prato. Intl.NumberFormat formata o preço como R$ 39,90.

Componente principal do micro: é ele que será exposto ao container. Envia só id, nome e preco, conforme o contrato.

CSS Modules (.module.css): as classes ganham nomes únicos, então o estilo de um micro nunca vaza para o outro. repeat(auto-fill, minmax(240px, 1fr)) faz o grid se adaptar sozinho à largura da tela.

_app.js envolve todas as páginas do Pages Router; é o único lugar onde o Next permite importar CSS global.

Página para testar o micro sozinho. Ela não é exposta ao container. O useEffect só loga os eventos para você conferir no console.

6Micro Pedido

Cópia exata do contrato do Cardápio. A duplicação é proposital: assim nenhum micro depende do código do outro.

  • addEventListener dentro do useEffect: começa a escutar o evento quando o componente aparece na tela.
  • return () => removeEventListener: para de escutar quando o componente sai. Sem isso, os itens seriam adicionados em dobro.
  • setItens((atuais) => ...): forma funcional, sempre trabalha com o estado mais recente.
  • Prato repetido aumenta a quantidade em vez de criar outra linha.

Componente exposto ao container. aria-live="polite" faz leitores de tela anunciarem o total quando ele muda.

7Module Federation nos micros

Agora transformamos os dois micros em remotes, expondo seus componentes principais.

  • webpack(config): o Next deixa você adicionar plugins ao webpack por aqui.
  • name: identidade do remote. Precisa ser igual ao usado no container.
  • filename: onde o remoteEntry.js será publicado.
  • exposes: './Cardapio' é o nome público; o valor é o arquivo real.
  • exposePages: false: não expõe as páginas do Next, só o que você listou.

Verificar se os remotes estão publicando

Abra primeiro localhost:3001 (em modo dev o Next só compila na primeira visita) e depois localhost:3001/_next/static/chunks/remoteEntry.js. Se aparecer código JavaScript, o remote está funcionando. Repita com -w pedido na porta 3002.

8Container App

  • remotes: formato nome@url-do-remoteEntry. A chave (cardapio) vira o prefixo do import: import('cardapio/Cardapio').
  • options.isServer: o Next compila duas vezes (servidor e navegador), e cada uma precisa do seu remoteEntry.js.

Error Boundary: isola falhas. Se um micro quebrar, só a área dele mostra o aviso; o resto da página continua funcionando. Precisa ser componente de classe (o React não tem hook para isso).

Mobile-first: o padrão é uma coluna; a partir de 900px vira duas colunas, com o pedido "grudado" no topo (position: sticky) enquanto você rola o cardápio.

  • lazy(() => import('cardapio/Cardapio')): carrega o componente do remote sob demanda, pela rede.
  • Suspense fallback: o que aparece enquanto o código do micro está sendo baixado.
  • noNavegador: o useEffect só roda no navegador, então os micros só são montados lá. Isso evita erros de hidratação do Pages Router com componentes remotos.

12Publicar no GitHub

Crie um repositório vazio e público em github.com/new (sem README, sem .gitignore). Depois, na raiz do projeto:

  • git init: transforma a pasta num repositório git.
  • git add . / commit: registra todos os arquivos (exceto os do .gitignore).
  • branch -M main: nomeia a branch principal como main.
  • remote add / push: liga ao repositório do GitHub e envia. Troque SEU-USUARIO pelo seu usuário.
Pasta docs/

A pasta docs/ (material de estudo) e o CLAUDE.md também vão para o repositório. Se não quiser publicá-los, adicione docs/ e CLAUDE.md ao .gitignore antes do git add ..

Confira no GitHub se o README aparece com o diagrama renderizado e envie o link na plataforma da EBAC.
